# ${注文}の多い珈琲店｜ダメな購入画面の手直しでプロダクト思考を学ぶ開発スタジオ

ダークパターンや不親切なUIを含む、わざと使いにくく作った購入画面を題材にした開発スタジオ基盤です。コードを書かずに、誰のために、何を優先し、どう成立させるかというプロダクトの意思決定サイクルを体験し、検証できます。

名前は宮沢賢治の『注文の多い料理店』から取りました。`${注文}` はプログラムで値を埋め込む書き方で、売上を求める店長と、望みも制約もさまざまな顧客から次々に届く注文を、作り手がどう受け止めて画面に落とし込むかを表しています。

![客層を選んだ直後の画面。左が手直しする購入画面、右が店長・お助けAI・お客さんとのチャット](docs/images/screen.jpg)

## コンセプト・背景

- **ダークパターンを生む板挟みと、生成AI時代の新しい壁**
  - 定期購入の罠や閉じにくい広告などのダークパターンは、悪意のある事業者だけでなく、売上目標と顧客の利益の板挟みに立った作り手の判断ミスや過失からも生まれます。生成AIの普及で、初学者でも初日から一応動く画面を世に出せるようになりました。一方で、LLMは頼まれなくても欺瞞的なUIを作りやすいことが知られています。数字と出典は次の課題の根拠にまとめています。
  - 判断までAIに丸投げすれば、気づかないうちにダークパターンを量産します。逆に迷って機能ごと消せば、定期便やクーポンを望んでいた顧客もお店も損をします。
- **プログラムの書き方の学習と、プロダクト設計の学習を分ける**
  - Scratch や基本構文の学習は、プログラムの構造や仕組み、つまり How を学ぶ場です。このスタジオは、売上を求める売り手と、ニーズも制約もさまざまな顧客の間で、だまさずに両方の望みをかなえるにはどう設計すべきか、つまり Why と What を練習する場です。
  - 学ぶ人はどこが悪いかを見つけ、誰のために何をかなえたいかを言葉にします。具体的な画面の直し方はAIが担います。AIが勝手に部品を選ぶことはなく、判断の主導権は常に人間が持ちます。
- **個人開発では得にくい、多面的なレビューとトレードオフの検証環境**
  - プロダクトを成立させるには、①ターゲットを決める → ②手を入れる → ③顧客の反応と売り手の成果の両面からレビューを受ける → ④トレードオフを判断して改善する、というサイクルが欠かせません。しかし個人開発や学習の場で、この環境を用意するのは困難です。
  - このスタジオには、依頼主の店長と、目的・身体の制約・要望の異なる9人の顧客ペルソナがいます。顧客は3つの客層に3人ずつ分かれ、実際に画面を操作するシミュレーションで反応します。1人でもプロダクト改善のサイクルを何度でも回せます。

### 課題の根拠

- **ダークパターンによる被害は減っていない**
  - 通販の定期購入の相談は、2023年度80,315件、2024年度89,401件、2025年度93,065件と毎年増えています[^kokusen-sub]。2025年度は65歳以上が46,958件、65歳未満が47,387件で、年齢を問わず起きています[^kokusen-65]。
  - 令和3年の特定商取引法改正で最終確認画面の表示が義務になった後も、定期購入の相談は高い水準のままです。消費者庁の検討会は、ダークパターンをより広く規制する方向で検討しています[^caa-interim]。
  - 28種類のダークパターンについて、見たことがある人の割合は平均で76.2%、過去12か月に経験した人は37.5%です[^caa-survey]。
- **悪意がなくても生まれる**
  - 同じ検討会は、問題のある表示には「事業者が意図的に用いるものだけでなく、過失等で結果的に消費者の意思決定を歪めるものも含まれ得る」としています。一方で、分かりやすい案内そのものは利便性にも役立つとしています[^caa-interim]。問題は定期便やクーポンという施策ではなく、見せ方です。
- **生成AIで増えうる**
  - LLMが作った通販サイトの部品1,296件のうち55.8%に欺瞞的なデザインがあり、売上を重視するよう指示すると有意に増えました[^chen]。検討会も、生成AIで表示を短期間に大量に作れるようになったことを挙げています[^caa-interim]。

## サンプル題材：コーヒー豆の通販画面

初期状態では、商品の説明と注文フォームが1ページにまとまった、単品通販の購入画面を題材にしています。

- **売上を伸ばしたい店長が付け足した画面から始まります。** 次の5つの問題が入っています。
  - 押しても反応しない注文ボタン
  - 点滅しながら減っては2:59に戻る、偽の売り切れまでの残り時間
  - 光る「今すぐ購入」のおとり
  - 数秒後に出るクーポン広告
  - 最初からチェックの入った定期便
- まず注文ボタンを直すと、0件だった注文が入るようになるという最初の成功体験が得られます。同時に、定期便の罠や広告による不満や後悔が表に出てきます。
- 定期便やクーポン広告は、初期の見せ方が悪質なだけです。毎月届く便利さや割引のお得さを求めているお客さんもいます。ただ削除すると誤って申し込む後悔はなくなりますが、それらを望んでいたお客さんが「毎月届けてほしいのに設定がなくて残念」「クーポンを使いたかったのに無くなってしまったのか」と不満を抱き、店長も売上が減ったことを嘆きます。
- 最初はチェックが外れていて条件が読める正直な定期便や、その場で割引が使えるクーポンのように、**使いやすい形に整えて残す**ことで初めて、選んだ3人全員の満足と店長の売上目標が両立します。
- **依頼主の店長が登場します。** 冒頭で事情を話し、どんなお客さんを一番大事にするかを尋ねます。手直しのたびに売上の立場から一言反応し、お客さんの反応を見るたびに注文数や定期便の件数をコードで数えて反応します。お客さんとお店の板挟みを体験できます。
- **顧客層は、購入画面で何を求めているかで分けています。** さっと買いたい人、確実に買いたい人、損をしたくない人の3つです。求めることがぶつかり合うので、誰を選ぶかが何を優先するかの判断になります。目が遠い、指が震える、細かい字を読む、定期便やクーポンを使いたい、といった違いは、一人ひとりの制約として持たせています。
- 練習用に、妨害要素の組み合わせを毎回ランダムにするモードもあります。妨害要素は、毎回必ず入るもの、現実の使いにくさ、冗談の3種類から選ばれ、壊れ方の多さを3段階から選べます。

| 難しさ | 妨害要素の数 | 冗談 | 向いている場面 |
| :--- | :--- | :--- | :--- |
| easy | 2〜3個 | なし | 初めての人、短い時間の体験会 |
| normal | 3〜5個 | 0〜1個 | 標準 |
| hard | 8〜9個 | 2個 | 慣れたチーム、何を捨てるかを強く迫りたいとき |

## 体験の流れ

1. **顧客層を選ぶ**
   - ページを開くと依頼主の店長が事情を話し、誰のために手直しするかを尋ねられます。選んだ客層の3人が来店し、それぞれの希望や困りごとを話します。
   - 授業や体験会などで公開ホストするときは、`VITE_PUBLIC_NOTICE=1` を設定すると、開始前に利用上の注意と集計への協力を尋ねるウィンドウが出ます。集計への協力は任意でチェックは最初から外れており、画面下部の このツールについて からいつでも切り替えられ、次の挑戦から反映されます。
2. **ダメ出しと質問**
   - スマートフォンの画面で気になる部品を赤ペンで囲むか、チャットに言葉で書きます。マイクで話して入力することもできます。
   - 入力欄の上で、話しかける相手を `お助けAI`、`店長`、`お客さん` から切り替えるか、`@店長` や `お客さん、` と呼びかけると、それぞれに直接質問や相談ができます。
   - 質問には、お助けAIが画面の実際の仕様にある事実だけで短く答えます。誰が喜ぶか、困るかといった判断は代弁しません。
   - 送った発言は、Gemini に渡す前に調べます。メールアドレスや電話番号などの個人情報や、AIへの決まりを書き換えようとする内容が見つかったら、送らずに知らせ、入力欄に戻します。
3. **手直しする**
   - 画面にある部品を手直しするときは、先にその部品を赤ペンで囲みます。どの部品の話かを取り違えないためで、囲まずに頼むと、お助けAIが囲むよう案内します。
   - どう直すかの具体的な指示だけでなく、誰のためにどうしたいかという目的を伝える指示も送れます。たとえば、うっかり定期便になるのを防ぎつつ、望む人は申し込めるようにしたい、という伝え方です。実装AIは、部品の削除・差し替え・追加・移動と状態の変更だけからなる最小限の差分を作り、画面を書き換えます。触っていない部品は変わらないので、手直ししてもデザインが崩れません。
   - チャットには、`` `注文を確定する` の押したときの動きを `反応なし` から `注文完了` に変更 `` のように、どの部品の何がどう変わったかが1行ずつ出ます。その行を押すと、スマートフォンの画面の該当する部品までスクロールして光ります。
   - 書き換えた画面は、描画できるか、注文を完了するボタンと合計金額が残っているか、対象外の部品が書き換わっていないかを検証します。問題があれば、直前の画面に自動で戻します。チャットの履歴から、好きな時点の画面に戻すこともできます。
   - 手直しの直後に、店長が売上の立場から一言反応します。
4. **お客さんの反応を見る**
   - 反応を見る前に、3人がそれぞれどうなるかを予想してから確かめることもできます。予想せずすぐ見ることもでき、予想したときは結果と突き合わせて、クリア時のレポートにも当たった数が出ます。
   - レビューAIは、これまでの会話や手直しの意図を知らされないまま、画面を実際に操作します。
   - ペルソナごとに、視界のぼかし、コントラストの低下、タップ位置のずれ、手数の上限、待てる時間、細かい字を読むか、定期便やクーポンを望んでいるか、といった制約があります。その制約のもとで操作をシミュレーションし、結果はコードが判定します。判定に使う部品の位置と大きさは、見えている画面ではなく、決まった大きさで画面の外に描き直して測ります。窓の大きさ、スクロール位置、広告が出ているかでは判定が変わりません。
   - 結果は4種類です。
     - 達成：嫌な思いをせずに買えた
     - 買えたけど不満：おとりを押した、罠に気づいて自分で外した、広告を閉じさせられた、欲しかった定期便やクーポンが消されていた、など
     - 離脱：途中でやめた
     - 後悔：罠に気づかずに買った
   - 選んだ3人全員が達成になるとクリアです。
   - Gemini は、操作の記録に沿って一人ひとりの感想を書くだけで、直し方は言いません。感想はお客さん本人の発言としてチャットに出ます。店長も注文数や定期便の件数に反応します。
   - あわせて、**選ばなかった客層の6人が今の画面を触ったらどうなるか**も1行で出ます。誰のために直したかで、別の誰かにどんな影響が出たかを確かめられます。
5. **トレードオフを判断して次の手直しへ**
   - まだ満足していないお客さんに理由を聞いたり、売上が減って困っている店長の意見を聞いたりしながら、ただ消すのではなく、誰のためにどう整えて残すかを判断して、次の手直しへ進みます。
   - 発言は、店長やお客さんへの質問と、画面の手直しの指示に分けて記録します。手直しの指示は、単純に消す、条件を決めて残す、具体的に直す、丸投げする、目的を伝える、といった型に分けます。型はコードの規則で決めるのが基本で、規則で決まらない指示だけを、Gemini Enterprise Agent Platform、旧称 Vertex AI の Text embeddings API で `text-multilingual-embedding-002` を使い、典型的な指示との近さを見て補います。
   - 指示に出てくる部品の名前や条件は、コードの規則で取り出し、Cloud Natural Language API の結果でも補います。取り出した語は題材の語彙に限り、人名などは残しません。通信に失敗したときや設定がない環境では、規則の結果だけを使います。
   - 記録には指示の文章を含めません。何を記録し、どこに送るかは、次の学習者の情報の扱いにまとめています。
   - 選んだ客層の3人全員が満足してクリアすると、レポートが出ます。LLMによる主観的な採点ではなく、質問した回数、直してと頼んだ回数、そのうち目的を伝えた回数、同じ所を直し直した回数、必要な機能を消した回数、1回で思いどおりに直った割合と、指示の出し方が変わった転換点を、実際の指示を引用して示します。選ばなかった客層の6人それぞれが、その画面をどう思いそうかも1行ずつ出ます。
   - 1回の挑戦は1つの客層で終わります。クリア後は、同じ客層でやり直すか、別の客層でやり直すかを選び、画面を最初の状態に戻してもう一度挑戦します。客層ごとのトレードオフや、指示の出し方の違いを比べられます。

## 学習者の情報の扱い

学習者を特定できる情報は、見えるかどうかに関係なく保持しない、を前提にしています。

- **指示の文章を残さない**：サーバー、Cloud Firestore、BigQuery のどこにも指示の文章を残しません。サーバーが持つのは、その挑戦の中で何番目の発言かだけです。クリア後のレポートで指示を引用するときは、サーバーが返す目印を、学習者のブラウザが手元の文章に置き換えて表示します。
- **集計は同意した挑戦だけ**：集計への協力にチェックを入れた挑戦だけ、指示の型、回数、結果を BigQuery に送ります。挑戦の始まりと終わり方も送り、クリアした、やり直した、タブを閉じた、30分操作しなかった、を区別して途中でやめた挑戦も数えます。うまくいった挑戦だけに集計が偏らないよう、同意は最初に1回尋ねます。集計した全体の傾向は、画面下部の みんなの集計 から誰でも見られます。指示の出し方のコツ、つまずきやすい所、見落としやすい所の3つにまとめ、根拠の数字を小さなタグで添えます。どの数字を根拠にするかはコードで決め、Gemini には見出しと本文の言い方だけを任せます。Gemini の文は、括弧がないか、見出しが15文字以内か、根拠にない数字がないかをコードで確かめ、外れていれば1回だけ作り直させ、それでもだめなら決まった文にします。コツは1時間ごとに作り直して保存するので、開くたびに Gemini を呼びません。個人の挑戦が推測されないよう、挑戦が3件未満の区分は集計から伏せ、コツの根拠には5件以上ある区分だけを使います。5件に満たないうちは集計中として、あと何件で表示されるかだけを出します。
- **一時的な記録は期限で消す**：1回の挑戦の振り返りに使う値は、挑戦ごとの乱数の番号で Cloud Firestore に置き、24時間で自動的に消えるようにします。独自のHTML部品をAIが読み取った結果だけは、同じ部品が毎回同じ判定になるよう期限なしで置きます。置くのは役割や文字の大きさといった決まった項目の値だけで、指示の文章や部品の中身は含みません。みんなの集計のコツも、集計の値とコツの文だけを1件置き、1時間ごとに上書きします。
- **送る前に止める**：メールアドレスと電話番号はコードの規則で止め、さらに Model Armor で個人情報、プロンプトインジェクション、有害な内容を調べます。止めた発言は会話の履歴から外し、以後 Gemini に渡しません。会話の履歴にある学習者の発言も合わせて調べるので、画面を通さずに送られた履歴から乗っ取られることも防ぎます。読み上げのAPIでも、個人情報にあたる文字列は外部の音声合成へ送らずブラウザの読み上げに切り替えます。
- **ログと保存を絞る**：サーバーのログにはエラーの種類と状態コードだけを出し、発言や Gemini の返事は出しません。判断の記録に自由に書かれた理由は保存せず、合成した音声も覚えておきません。接続元のIPアドレスは、呼び出し回数の上限を数えるためにメモリで扱うだけで、保存しません。
- **受け付ける値を絞る**：挑戦の番号、客層、会話の履歴、お客さんの反応の記録は、決まった形と長さのものだけを受け付けます。

Cloud Firestore、BigQuery、Cloud Natural Language API、Sensitive Data Protection と連携した Model Armor はこのプロジェクトで有効にしてあり、設定がないローカル環境でもメールアドレスと電話番号の規則による確認や手元での振り返りがそのまま動きます。

## 使用テストの結果と限界

この仕組みが、ただ消すことから、誰のためにどう残すかへの変化を生むかを確かめました。2026年11月8日に、ツールの狙いを知らせずに、AIエージェント3人に使ってもらいました。

- **やり方**
  - 人物像の違う3人を、Claude が2人、Gemini が1人演じました。UIの授業を取り始めた文学部生、販促を担当する社会人、生成AIで個人開発をする情報系学部生です。
  - ブラウザの画面を見て、クリックと入力だけで操作してもらいました。少なくとも2回挑戦したあと、5段階の評価と自由記述に答えてもらいました。
  - 遊ぶ前と後に、同じ問いに答えてもらいました。自動でプレミアム会員に移行するチェック欄がある申し込み画面を、会員を増やしたい運営の立場でどう直すか、という問いです。
- **選ばなかった客層への影響**：3人とも2回クリアしました。クリアした画面で、選ばなかった客層の6人のうち満足しそうな人は、1回目の3人・2人・2人から、2回目はいずれも5人に増えました。
- **指示の出し方**：2回目は、3人中2人が手直しの前に店長やお客さんへ質問しました。質問の回数は、それぞれ0回から2回、0回から3回に増えました。もう1人は、店長の売上の事情とお客さんが嫌がる理由を添えて指示しました。
- **遊ぶ前と後の答え**：遊ぶ前に、初期チェック自体は残すかもしれないと答えた人が、遊んだ後はチェックを外し、プレミアムの良さが伝わる案内を画面内に置くと答えました。ほかの2人も遊んだ後は、機能をなくさずに条件を分かるようにして自分で選んでもらうことと、その方が会員が残るという理由を加えました。
- **5段階の評価**：何をするツールかすぐ分かったは3・4・5、達成感があったは4・4・4、待ち時間は気にならなかったは3・3・2でした。

**限界**：人ではなくAIによる3人分のテストで、統計的な効果を示すものではありません。2回目はいずれも損をしたくない人の客層を選んでいて、1回目と客層が違うため、変化には客層の違いも含まれます。また、テストのあとで、感想と判定の食い違いや待ち時間の表示など、見つかった問題を直しています。

## 3つのAIの役割分担

| 役割 | 入力 | 出力と制約 |
| :--- | :--- | :--- |
| **お助けAI**：質問への回答と振り分け | 今のアプリの仕様、画面のスクリーンショット、赤ペンで囲んだ画像、対象の部品、会話の履歴、発言 | 仕様にある事実だけの短い回答と、説明つきの手直しの候補。何もしないという候補も含む。判断や代弁はしない |
| **実装AI** | 具体的な指示か目的を伝える指示、今のアプリの仕様、対象の部品、会話の履歴 | 最小限の差分を作る。書き換えた画面を検証し、失敗したら自動で戻す |
| **レビューAI** | 画面の状態、スクリーンショット、制約のもとで実行した操作の記録。会話の履歴は渡さない | コードが判定した達成・不満・離脱・後悔と、操作の記録の事実に沿った、一人ひとりの感想 |

## Google技術を選んだ理由

このプロダクトでは、学ぶ人が誰のために何をかなえたいかを言葉にし、画面の直し方はAIが担います。そのためAIには、自由な文章ではなく、検証できる形で画面を書き換えることが求められます。一方で、お客さんが買えたかどうかの判定までAIに任せると、同じ画面でも結果が揺れて練習になりません。

| 使っている技術 | 何に使うか | 選んだ理由 |
| :--- | :--- | :--- |
| **Gemini**：Agent Platform 経由、`@google/genai` | お助けAI、実装AI、レビューAIのすべてと、独自のHTML部品の読み取り、マイク音声の聞き取り | 画面の差分を検証できる形で返せること、赤ペンで囲んだ画像や音声を読めること、待ち時間が短いことの3つがそろう。詳しくは表の下 |
| **Gemini Enterprise Agent Platform** | Gemini と埋め込みの呼び出し | 画面側にAPIキーを置かず、Cloud Run のサービスアカウントで認証できる。利用枠と費用をプロジェクトごとに管理できる |
| **Agent Platform の Text embeddings API**：`text-multilingual-embedding-002` | 規則で分類できなかった指示の型を、典型的な指示との近さで補う | 指示の型は規則で決めるのが基本。規則に当てはまらない言い回しだけを、多言語対応の埋め込みで補う |
| **Cloud Text-to-Speech** | 店長、お助けAI、お客さん9人の、11人分の声 | 誰が話しているかを声で区別でき、文字を読むのが苦手な人も会話を追える |
| **Model Armor**：Sensitive Data Protection と連携 | 学習者の発言を Gemini に渡す前に調べる | 生成AIのアプリ向けの検査で、個人情報とプロンプトインジェクションと有害な内容をまとめて止められる。学習者が自由に書く欄があるので、個人情報を受け取らない仕組みが要る |
| **Cloud Firestore**、**BigQuery** | 挑戦ごとの一時的な記録と、同意した挑戦の集計、独自のHTML部品の読み取り結果 | 挑戦の記録を期限つきで置けるので、Cloud Run のインスタンスをまたいでも振り返りが欠けない。読み取り結果は先に書いたものだけを残すので、インスタンスが複数あっても同じ部品の判定がそろう。BigQuery ではクラス全体の変化を、サーバーを管理せずに SQL で集計できる |
| **Cloud Run** | 画面とAPIを1つのコンテナで配信する | ビルド済みの画面とAPIサーバーを `Dockerfile` 1つで出せる。最小インスタンス数を0にすれば、使われないときの費用がかからない |

Gemini では、次の機能を使っています。

- **Structured Outputs**：実装AIが返す画面の差分を、スキーマで決めた形で受け取ります。部品の追加・削除・差し替えと状態の変更だけなので、適用する前にコードで検証し、壊れていれば自動で戻せます。触っていない部品が変わらないことも確かめられます。
- **画像と音声の入力**：赤ペンで囲んだ画像と画面のスクリーンショットを、指示と一緒に読みます。初学者は部品の名前を知りませんが、ここ、と囲むだけで、どの部品の話かを伝えられます。マイクで話した音声もそのまま聞き取って入力欄の言葉に整えます。
- **Function Calling**：客層の選択など、人間が下した判断を `record_human_decision` で決まった項目に残します。応答がないときは、入力どおりに保存します。
- **Flash モデルと考える量の指定**：直して反応を見ることを何度も繰り返すので、待ち時間が短いことを優先し、考える量は既定で LOW にしています。実測では、手直しはおおむね3〜7秒で返ります。

AIに任せないことも、はっきり分けています。お客さんが買えたか、途中でやめたか、後悔したかは、部品の役割と、視力・指の震え・手数の上限といった一人ひとりの制約から、コードが判定します。Gemini は、その判定と操作の記録に沿った感想の言葉だけを書きます。学ぶ人が独自のHTML部品を足したときは、Gemini がその部品を、クーポンか定期便か、自分で選べるか、文字や押せる部分の大きさ、気づかないと損をする条件があるか、といった決まった項目に読み取り、判定はほかの部品と同じ基準でコードが行います。読み取り結果は部品ごとに保存して使い回すので、同じ画面なら同じ結果になり、直し方の違いを比べられます。

## ハッカソンでの拡張・カスタマイズ箇所

題材を差し替えるときは、[`src/shared/themes/coffeeBeans.ts`](src/shared/themes/coffeeBeans.ts) を参考に題材ファイルを1つ書き、[`src/shared/initialTheme.ts`](src/shared/initialTheme.ts) の `ACTIVE_THEME` を切り替えます。題材ファイルには次のものを書きます。

- 妨害要素を入れる前の画面。部品、状態、合計金額などの計算式
- 妨害要素の候補と、毎回入れるもの・現実の使いにくさ・冗談の区別、難しさごとに選ぶ数
- 固定の問題として妨害要素を名前で並べたものと、既定で使う問題
- 店長のセリフと、お客さんの反応を見るたびに数える定期便の件数などの数字
- 顧客層とペルソナ、一人ひとりの制約
- 冒頭で進行役が話す行と、実装AIへの題材特有の補足

画面の部品には、本物のボタン、おとり、危険なボタン、必須の入力欄、関係ない項目、罠、合計、ポップアップといった役割を付けます。操作シミュレーターは部品のIDではなく役割を見て判定するので、題材を変えてもシミュレーターを書き換える必要はありません。

画面の見た目は、描画を受け持つ [`src/client/sandboxRenderer.ts`](src/client/sandboxRenderer.ts) と [`src/client/style.css`](src/client/style.css) が持ちます。題材のデータには、部品の種類と設定だけを書きます。

- 元のデザインは、専門店らしい温かみのある購入画面です。手順の表示、商品カード、選べるカード、金額の内訳、画面下に固定した合計と購入ボタンなどの部品で組み立てます。
- 妨害要素には `style.skin: 'intrusive'` を付けます。元のデザインの決まりを無視した、後から付け足したような見た目で描かれます。定期便の罠のように気づかれにくくしたいものには、あえて付けずに元のデザインに溶け込ませます。
- 実装AIは部品単位の差分だけを返し、部品の種類と設定を変えるだけなので、手直ししてもデザインの品質は崩れません。

そのほかの主な拡張箇所は次のとおりです。

- [`src/shared/types.ts`](src/shared/types.ts)：UI部品の種類、役割、操作したときの動き、アクションの型定義
- [`src/shared/appRuntime.ts`](src/shared/appRuntime.ts)：計算式、表示条件、アクションの実行規則。画面の描画と操作シミュレーターで共有する
- [`src/client/sandboxRenderer.ts`](src/client/sandboxRenderer.ts)：スマートフォンの画面の中での部品の描画と、操作したときの処理
- [`src/shared/sandboxValidator.ts`](src/shared/sandboxValidator.ts)：画面の整合性の検査と、部品の役割にもとづく操作シミュレーション
- [`src/shared/customComponentProfile.ts`](src/shared/customComponentProfile.ts)：独自のHTML部品を判定に使うための決まった項目と、HTMLから動きを読み取る規則
- [`src/server/customComponentProfiles.ts`](src/server/customComponentProfiles.ts)：独自のHTML部品の読み取り結果をサーバーのメモリと Cloud Firestore に固定し、評価のたびにぶれないようにする
- [`src/shared/prediction.ts`](src/shared/prediction.ts)：お客さんの反応を見る前の予想と、結果との突き合わせ
- [`src/shared/promptTelemetry.ts`](src/shared/promptTelemetry.ts)：質問と手直しの指示の区別、指示の型の分類、直し直しの判定、クリア時の記録の集計
- [`src/shared/aggregateTips.ts`](src/shared/aggregateTips.ts)：みんなの集計のコツ。根拠のタグの決め方、Gemini の文の確かめ方と作り直し、決まった文
- [`src/server/aggregateTips.ts`](src/server/aggregateTips.ts)：みんなの集計のコツを1時間ごとに作り直し、サーバーのメモリと Cloud Firestore に保存する
- [`src/server/gemini.ts`](src/server/gemini.ts)：3つのAIのプロンプト、Structured Outputs のスキーマ、発言の意図の判定、Function Calling による判断の記録
- [`src/server/store.ts`](src/server/store.ts)：規則による分類と抽出、それを補う Agent Platform の Text embeddings API と Cloud Natural Language API、Cloud Text-to-Speech、BigQuery、Cloud Firestore との連携
- [`src/server/rateLimit.ts`](src/server/rateLimit.ts)：予期しないトラフィックへの守り。1分あたりと1日あたりの呼び出し回数、同時に処理する数、本文の大きさ、呼び出し元の確認
- [`src/server/modelArmor.ts`](src/server/modelArmor.ts)：発言を Gemini に渡す前に、規則と Model Armor で調べて止める
- [`src/server/logSafe.ts`](src/server/logSafe.ts)：ログに発言や返事を出さないための、エラーの書き方
- [`src/server/api.ts`](src/server/api.ts)：APIの入口。受け付ける値の形と長さの確認、送る前の検査、回数の上限

## 技術構成

![システムアーキテクチャ図。学習者のブラウザから Cloud Run を通して、Model Armor、Gemini、Text Embeddings API、Cloud Natural Language API、Cloud Text-to-Speech API、Cloud Firestore と BigQuery を呼び出す](docs/images/architecture.png)

- **フロントエンド**：TypeScript / Vite / HTML5 Canvas / Sandbox `iframe`
- **生成AI・音声**：`@google/genai` で Gemini Enterprise Agent Platform の Gemini を呼ぶ。赤ペンで囲んだ画像、画面のスクリーンショット、マイク音声のマルチモーダル入力、Structured Outputs、Function Calling の `record_human_decision` / Google Cloud Text-to-Speech API で11人分の声を合成し、決まったセリフの音声は同梱
- **LLMを使わない分析と記録**：規則による分類と、それを補う Agent Platform の Text embeddings API / 規則によるキーワード抽出と、それを補う Google Cloud Natural Language API / 指示の文章を含まない記録を、Cloud Firestore に期限つきで置き、同意した挑戦だけ BigQuery に送る
- **実行環境と安全性**：Google Cloud Run 向けのコンテナ構成 / CSP ヘッダー、Sandbox `iframe` による分離、対象外の部品が変わらないことの検証と自動で戻す仕組み / Gemini と読み上げと記録のAPIの呼び出し回数の上限。接続元ごととサーバー全体の1分あたりで数え、`.env.example` の `RATE_LIMIT_*` で変えられる / Gemini を呼ぶ1日あたりの上限による費用の非常停止、接続元ごとの同時に処理する数の上限、APIごとの本文の大きさの上限、ほかのサイトの画面からの呼び出しを断る確認 / Model Armor と規則による、送る前の個人情報とプロンプトインジェクションの検査 / 受け付ける値の形と長さの確認
- **品質と衛生管理**：Node.js Test Runner / `scripts/check-hygiene.mjs` によるコミット、機密情報、ローカルパスの混入の検査

## セットアップ・起動方法

### 1. パッケージのインストール

```bash
npm install
```

### 2. 環境変数の設定

`.env.example` を `.env.local` にコピーし、Gemini API キーか Google Cloud プロジェクトを設定します。AIを使う機能はどれも接続の設定が必要で、設定していないとチャットにエラーメッセージが出ます。

```bash
cp .env.example .env.local
```

```env
GEMINI_API_KEY=your_gemini_api_key
```

Google Cloud のプロジェクトで動かすときは、`.env.example` にある次の値も設定できます。どれも任意で、設定しなければその連携は働かず、ほかの機能はそのまま動きます。

- `MODEL_ARMOR_LOCATION`、`MODEL_ARMOR_TEMPLATE_ID`：送る前の検査に使う Model Armor のテンプレート
- `BIGQUERY_DATASET`、`BIGQUERY_TABLE`、`BIGQUERY_RUN_TABLE`：集計を送る BigQuery のデータセットとテーブル
- `FIRESTORE_ENABLED`：`0` にすると Cloud Firestore に送らない
- `RATE_LIMIT_*`：1分あたりと1日あたりの呼び出し回数、同時に処理する数の上限
- `ALLOWED_ORIGINS`：このサイトのほかに、API を呼んでよい画面
- `VITE_PUBLIC_NOTICE`、`VITE_OPERATOR_*`：公開ホスト時に起動時の利用上の注意と集計への同意ウィンドウを出し、運営者情報を表示する設定

### 3. 開発サーバーの起動

```bash
npm run dev
```

ブラウザで `http://localhost:5173` を開くと、スタジオの画面が表示されます。

- 何も付けなければ、売上を伸ばしたい店長の画面という固定の問題から始まります。題材に別の問題を足したときは、`?scenario=問題の名前` で選べます。発表のデモ用には、罠を広告と定期便に絞った `?scenario=demo` があります。
- `http://localhost:5173/?mode=random` を開くと、妨害要素の組み合わせが毎回ランダムになる練習用のモードになります。`&level=easy` のように `easy`・`normal`・`hard` を付けると壊れ方の多さを、`&seed=123` のように数字を付けると組み合わせの固定を選べます。
- `http://localhost:5173/?clean` を開くと、妨害要素を入れる前の画面を確認できます。題材のデザインを調整するときに使います。

### 4. テスト・ビルド・衛生チェック

```bash
npm test              # ユニットテストとコミット衛生テストの実行、AIには接続しない
npm run typecheck     # TypeScript の型チェック
npm run build         # 本番ビルド
npm run check:hygiene # 機密情報、ローカルパスの混入、コミット規約のチェック
```
